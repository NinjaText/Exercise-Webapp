# Inmotus RX Mobile App (Capacitor) — Design Spec

**Date:** 2026-09-20
**Branch:** `mobile-app-capacitor`
**Status:** Approved design, pending implementation plan

## 1. Goal

Ship Inmotus RX to the Apple App Store and Google Play as a native app for both
trainers and clients, without rewriting the product. The app is a Capacitor
shell that loads the production Next.js app from `https://app.goinmotus.com`
inside a native web view, plus a native-aware layer in the web app so the
experience feels like a first-class mobile app rather than a website in a box.

### Non-goals (v1)

- Native in-app purchases. Billing stays web-only (see §7).
- Offline data or offline workout logging. Only a graceful offline screen.
- Tablet layouts. iPhone and Android phones only.
- A full mobile program builder or drag-to-reschedule calendar. Heavy
  authoring tools stay desktop-first and degrade gracefully on phones (see §5a).
- A separate React Native client. If offline logging, HealthKit, or watch
  support are ever required, that is a new project with its own spec.

### Decisions already made

| Decision | Choice |
|---|---|
| Audience | Both roles in one app |
| Shell | Capacitor, remote URL (no static export) |
| Push backend | Firebase Cloud Messaging via `firebase-admin` |
| Billing in app | None. Neutral "manage on the web" screen |
| Offline | Bundled retry page + in-session banner |
| Store accounts | Not yet created; enroll as an organization |
| App name | Inmotus RX |
| Production URL | `https://app.goinmotus.com` |
| Bundle / application ID | `com.goinmotus.app` |
| Custom URL scheme | `inmotus://` |

## 2. Architecture overview

```
┌───────────────────────────────┐        ┌──────────────────────────────┐
│ Native shell (mobile/)        │        │ Next.js app (Vercel)         │
│  iOS + Android projects       │  HTTPS │  app.goinmotus.com           │
│  Capacitor runtime + plugins  │◀──────▶│  Clerk, Prisma, Pusher, S3   │
│  Bundled offline page         │        │  Native-aware layer (new)    │
│  Push token, deep links,      │        │  Push service (new, FCM)     │
│  splash, status bar, haptics  │        │  Mobile config endpoint (new)│
└───────────────────────────────┘        └──────────────────────────────┘
                 │  device token                          ▲
                 ▼                                        │ firebase-admin
          ┌─────────────┐   APNs / FCM   ┌────────────────┴───┐
          │ Apple / Google│◀──────────────│ Firebase Cloud Msg │
          └─────────────┘                └────────────────────┘
```

The web app is the product. The shell contributes only what a browser cannot:
store presence, push tokens, splash, status bar, haptics, deep links, and a
file save/share bridge. Every UI change lives in the Next.js codebase and
ships with a normal Vercel deploy. The shell is rebuilt and resubmitted only
when native configuration, plugins, icons, or the minimum-version policy change.

### capacitor.config.ts (essentials)

```ts
const serverUrl = process.env.CAP_SERVER_URL ?? "https://app.goinmotus.com";
const config: CapacitorConfig = {
  appId: "com.goinmotus.app",
  appName: "Inmotus RX",
  webDir: "www",
  server: {
    url: serverUrl,
    cleartext: serverUrl.startsWith("http://"),   // dev only
    errorPath: "offline.html",
    allowNavigation: ["app.goinmotus.com", "*.goinmotus.com", "*.clerk.accounts.dev"],
  },
  ios: { appendUserAgent: `InmotusApp/${version} (ios)`, contentInset: "never" },
  android: { appendUserAgent: `InmotusApp/${version} (android)` },
  plugins: {
    SplashScreen: { launchAutoHide: false, launchShowDuration: 0 },
    PushNotifications: { presentationOptions: [] },   // foreground handled in-app
    Keyboard: { resize: "body" },
    StatusBar: { overlaysWebView: true },
  },

```

`allowNavigation` must include the production Clerk frontend API and accounts
domains once known (e.g. `clerk.goinmotus.com`, `accounts.goinmotus.com`).
Anything not listed opens in the system browser, which would break sign-in.

## 4. Native detection in the web app

Two signals, one contract.

**Server side.** `lib/native/platform.ts`

```ts
export type NativePlatform = "ios" | "android";
export interface NativeInfo { isNative: boolean; platform?: NativePlatform; appVersion?: string }
export function parseNativeUserAgent(ua: string | null): NativeInfo   // pure, unit-tested
export async function getNativeInfo(): Promise<NativeInfo>            // reads headers()
```

Parses the `InmotusApp/<version> (<platform>)` suffix. Used in layouts and
pages that must branch during render (billing gate, sign-in page, settings).

**Client side.** `components/providers/native-provider.tsx`

- Context value: `{ isNative, platform, appVersion, isOnline }`.
- Reads `Capacitor.isNativePlatform()` and `Capacitor.getPlatform()` from
  `@capacitor/core`, which is safe to import in a browser (returns `web`).
- Registers all native listeners in one place: app state, back button,
  `appUrlOpen`, network status, push events.
- Hides the splash on mount (first client render) with a 5 s failsafe.
- Dev escape hatch: `?native=ios|android` query param plus `localStorage`
  flag forces native mode in a desktop browser. Disabled in production builds
  unless `NEXT_PUBLIC_NATIVE_DEBUG=1`.

`hooks/use-native.ts` exports `useNative()`. No component checks user agent or
Capacitor directly.

`@capacitor/core` and the plugin packages used from web code are added as root
dependencies. They are small and no-op on web.

## 5. Navigation and feel

### Bottom tab bar

`components/layout/mobile-tab-bar.tsx`, shown on viewports below `lg` for both
mobile web and native. Fixed to the bottom, respects `env(safe-area-inset-bottom)`.

| Role | Tabs |
|---|---|
| Client | Dashboard · Programs · Calendar · Nutrition · Inbox |
| Trainer | Dashboard · Clients · Programs · Inbox · More |

"More" opens a bottom sheet with Exercises, Nutrition, Analytics, Settings, and
Admin when `isSuperAdmin`. Inbox shows the existing unread badge. The active
tab derives from the pathname. Tab items are derived from the same nav arrays
as `sidebar.tsx`, refactored into `components/layout/nav-items.ts` so the two
never drift.

The `Header` keeps its menu button on small screens for secondary navigation
(Settings, Organization, Billing on web, Audit Log, Super Admin). The tab bar
owns primary navigation; the sheet owns everything else.

### Safe areas and chrome

- Root layout viewport: `viewport-fit=cover`; on native also `maximum-scale=1`.
- CSS variables `--safe-top/--safe-bottom` from `env()`; header, tab bar, and
  bottom sheets consume them.
- Status bar style follows `next-themes` (`StatusBar.setStyle` on theme change).
- Native-only CSS (scoped by `html[data-native]`): `-webkit-touch-callout: none`,
  `overscroll-behavior: none` on body, `user-select: none` on nav chrome, and
  `font-size >= 16px` on inputs to prevent iOS focus zoom.

### Launch and lifecycle

- Splash stays until `NativeProvider` mounts, then `SplashScreen.hide()`.
- `appStateChange` → active after more than 5 minutes in background calls
  `router.refresh()`. Pusher reconnects on its own.
- Android back button: `history.back()` when history exists, otherwise
  `App.minimizeApp()` at a tab root.
- Haptics: light impact on set completion and check-in submit via a tiny
  `haptic()` helper that no-ops on web.

### Links and downloads

- A capture-phase click listener in `NativeProvider` opens external-origin
  `<a>` targets with `Browser.open()`.
- `lib/native/download.ts` exports `saveOrDownload(blob, filename)`. On web it
  performs today's anchor download. On native it writes to the cache
  directory with `Filesystem` and calls `Share.share()`. Call sites:
  `program-detail-view.tsx`, `program-list-client.tsx`, `meal-log-dialog.tsx`,
  and any other `createObjectURL` + `download` pattern found during
  implementation. The "Print" action opens the PDF URL in the system browser
  on native.

### Media

- Voice memos use `MediaRecorder`; WKWebView requires
  `NSMicrophoneUsageDescription`, Android requires `RECORD_AUDIO` and
  `MODIFY_AUDIO_SETTINGS`. File inputs need `NSCameraUsageDescription` and
  `NSPhotoLibraryUsageDescription`.
- Video: `allowsInlineMediaPlayback` stays on (Capacitor default). YouTube
  embeds via react-player are verified on device in QA.

## 5a. Trainer mobile experience

Trainers will use the app between sessions and from the gym floor, and the
App Store reviewer will exercise trainer flows with the demo account. Every
trainer route must therefore be either genuinely usable on a phone or
gracefully read-only. Nothing may render broken.

### Audit first

Before any redesign, walk every trainer route at 390 px width (iPhone 15
class) and record one of three states per screen: works, cramped, broken.
The audit result becomes the task checklist for this section. Routes:
dashboard, clients, clients/[id] (all tabs), programs, programs/[id],
exercises, nutrition, messages, analytics, calendar, sessions/[id],
check-ins, habits, assessments, settings and subpages.

### Tier 1 — phone-first, redesigned

What trainers actually do on a phone. Single-column layouts, sticky primary
action, bottom sheets instead of side panels, 44 px touch targets.

- Inbox and message threads, including voice memo record and playback.
- Clients list (search, filter, status badges) and client detail: overview,
  today's and this week's workouts, recent check-ins, pain summary, notes.
- Today's and this week's schedule (list form, not the big calendar grid).
- Check-in review: read responses, comment, mark reviewed.
- Completed workout review with set-level data and client feedback.
- Quick assign: attach an existing program or template to a client and pick
  a start date.
- Notifications list.

### Tier 2 — phone-usable, view and light edit

- Program detail: readable week/day/exercise structure; edit sets, reps,
  load, notes, or swap an exercise via a bottom sheet. No reordering.
- Exercise library: search, filter, view detail and video; add to favorites.
- Analytics: charts stack vertically, one per card, horizontally scrollable
  where dense; filters move into a sheet.
- Nutrition review for a client.
- Settings pages.

### Tier 3 — desktop-only, gracefully

- Full program builder (drag-and-drop), calendar drag-to-reschedule, bulk
  exercise import, clinic/admin management, AI program generation wizard.
- On phones these render a read-only view of the same data plus a
  `DesktopOnlyNotice` card: "This tool is built for a larger screen. Open
  Inmotus RX on a laptop to edit." No disabled drag handles, no clipped
  toolbars. A shared `useIsPhone()` breakpoint hook decides.

### Rules

- Tiering is by route and is recorded in `components/layout/nav-items.ts`
  next to each entry so the tab bar's "More" sheet can label desktop-only
  tools.
- Tier 1 screens get a manual QA pass on both devices; Tier 3 screens are
  checked for the notice and for zero horizontal overflow.
- The client experience is already phone-first; this section does not change
  it beyond the shared navigation in §5.

## 6. Authentication

- Clerk is unchanged. The web view loads the real domain so the session cookie,
  middleware in `proxy.ts`, and server actions behave exactly as in Safari.
- **Native builds show email-based sign-in only.** Google OAuth rejects
  Android WebView user agents, and Apple guideline 4.8 requires Sign in with
  Apple whenever any third-party login is offered. `sign-in` and `sign-up`
  pages read `getNativeInfo()` and pass a Clerk `appearance` that hides the
  social buttons block. Email + password and email code both work.
- Clerk dashboard: raise session inactivity timeout (recommend 30 days) so
  users are not signed out weekly.
- Sign-out (Clerk `signOut`) first calls `unregisterPushDevice` for the
  current token (see §8) so a shared device stops receiving the previous
  user's notifications.
- **Account deletion (Apple 5.1.1(v)).** Not present today. Add
  `Settings → Account → Delete account` for both roles, available on web and
  native: confirm dialog, `deleteOwnAccountAction` that anonymizes or removes
  the user's data per existing deactivation semantics, deletes push devices,
  deletes the Clerk user via backend API, and redirects to
  `/account-deactivated`. Trainers who still have active clients are blocked:
  the dialog lists the count and links to the Clients page to deactivate or
  reassign them first. No cascade deletion of client data in v1.
- **Legal pages.** Add `/privacy` and `/terms` public routes, linked from
  the site footer and from Settings. Required by both stores and by Clerk's
  sign-up page on native.

## 7. Billing gate on native

Trainers with an active subscription are unaffected. The platform layout
currently redirects on expired trial or failed payment to
`/billing?reason=…`. Change:

- `app/billing/page.tsx` reads `getNativeInfo()`. On native it renders
  `SubscriptionAttentionScreen`: headline "Your subscription needs attention",
  one sentence explaining the reason, "Manage your subscription from your
  account on the web", and a Sign out button. No prices, no checkout, no
  outbound link, no Stripe script.
- `/billing/success` and `/billing/cancel` are unreachable from native; if hit
  they redirect to `/dashboard`.
- Settings hides the Billing entry and any "Upgrade" prompts when native.
- The public program purchase page `/p/[slug]` renders program details but
  replaces the Buy button with "Available for purchase on the web" on native.
- `/api/checkout/program` rejects requests carrying the native UA marker with
  403, as defense in depth.

## 8. Push notifications

### Data model

```prisma
enum PushPlatform { IOS ANDROID }

model PushDevice {
  id         String       @id @default(auto()) @map("_id") @db.ObjectId
  userId     String       @db.ObjectId
  user       User         @relation("PushDevices", fields: [userId], references: [id])
  token      String       @unique
  platform   PushPlatform
  appVersion String?
  lastSeenAt DateTime     @default(now())
  createdAt  DateTime     @default(now())

  @@index([userId])
}
```

`User` gets `pushDevices PushDevice[]` and `pushEnabled Boolean @default(true)`.

### Registration flow (client)

1. `NativeProvider` exposes `requestPushPermission()`.
2. A soft pre-prompt sheet ("Get reminders for workouts and messages") is shown
   once, after the user has completed onboarding and reached the dashboard for
   the second time, or immediately when they toggle notifications on in
   Settings. Dismissal is remembered in `localStorage`; never nag again.
3. On accept: `PushNotifications.requestPermissions()` → `register()`.
4. `registration` event → server action `registerPushDeviceAction({ token,
   platform, appVersion })` which upserts by token (handles rotation and
   device handoff between users).
5. On every native app launch with permission already granted, `register()`
   is called again to refresh `lastSeenAt` and pick up rotated tokens.
6. Settings → Notifications toggle: off calls `unregisterPushDeviceAction`
   for the current token and sets `pushEnabled=false`; on re-registers.
7. Sign-out unregisters the current token.

### Sending (server)

`lib/services/push.service.ts`

```ts
export interface PushMessage { title: string; body?: string; link?: string; data?: Record<string,string> }
export function buildPushPayload(devices, msg, badge): MulticastMessage   // pure, unit-tested
export async function sendPushToUser(userId: string, msg: PushMessage): Promise<void>
```

- Loads the user's devices; returns early if none or `pushEnabled=false`.
- Badge = unread notifications + unread messages, computed at send time.
- iOS payload includes `apns.payload.aps.badge` and `sound: "default"`;
  Android uses channel `default` with high importance.
- `sendEachForMulticast`; tokens failing with
  `messaging/registration-token-not-registered` or `invalid-argument` are
  deleted.
- All errors are caught and logged with a `[push]` prefix. Push never throws
  into a caller.
- Firebase Admin is initialized lazily from `FIREBASE_SERVICE_ACCOUNT_JSON`
  (base64 of the service account file). Missing env → push service logs once
  and becomes a no-op, so local dev works without Firebase.

### Triggers

- `createNotification` in `notification.service.ts` calls `sendPushToUser`
  inside `after()` from `next/server` so the response is not delayed. Every
  existing notification type (sessions, nutrition, compliance, reminders,
  cron nudges) pushes with no further changes.
- `sendMessageAction` pushes the recipient directly ("New message from
  {sender}", link to the thread). Voice memos reuse the same path.
- No push is sent to the acting user's own devices.

### Receiving (client)

- `pushNotificationReceived` (foreground): show a Sonner toast with the title
  and a "View" action navigating to `data.link`. System banner suppressed via
  `presentationOptions: []`.
- `pushNotificationActionPerformed` (tap, including cold start):
  `router.push(data.link ?? "/dashboard")`. On cold start the listener is
  registered before Capacitor delivers the queued event; verified in QA.
- On `appStateChange → active` and after any push tap, `Badge.clear()`.

### Firebase setup (ops)

Firebase project `inmotus-rx`; Android app with `google-services.json`; iOS app
with `GoogleService-Info.plist`; APNs auth key (.p8) uploaded to Firebase
Cloud Messaging settings. Both files are git-ignored and documented in
`mobile/README.md`. iOS target enables Push Notifications and Background
Modes → Remote notifications capabilities.

## 9. Deep links, version gate, offline

### Universal links / App Links

- `public/.well-known/apple-app-site-association` (JSON, no extension, served
  as `application/json` via a header rule) listing `TEAMID.com.goinmotus.app`
  with paths `/dashboard/*`, `/programs/*`, `/messages/*`, `/calendar/*`,
  `/sessions/*`, `/nutrition/*`, `/p/*`, `/onboarding/*`, `/sign-in`.
- `public/.well-known/assetlinks.json` with the Android signing cert SHA-256.
- iOS Associated Domains `applinks:app.goinmotus.com`; Android intent filter
  with `autoVerify`.
- Custom scheme `inmotus://` as fallback for QA and marketing.
- `appUrlOpen` handler maps the URL path onto `router.push`.

### Version gate

- `app/api/mobile/config/route.ts` (public, cached 5 min) returns
  `{ minSupportedVersion: { ios: "1.0.0", android: "1.0.0" }, storeUrls: {...} }`.
  Values come from env `MOBILE_MIN_VERSION_IOS/ANDROID` so a bump is a Vercel
  env change, not a deploy.
- `NativeProvider` fetches it on launch and on resume; if `appVersion` is
  lower, render a full-screen `UpdateRequiredScreen` with the store link.
  Store links are permitted content.

### Offline

- Cold start with no network: Capacitor shows `offline.html` (Retry reloads
  `server.url`; auto-retries every 5 s while `navigator.onLine`).
- In session: `Network.addListener("networkStatusChange")` drives `isOnline`;
  a thin top banner "No internet connection" appears and disappears. Forms are
  not disabled; server-action failures surface through existing error handling.
- Existing `app/(platform)/error.tsx` is verified to render a working "Try
  again" in the web view.

## 11. Environments and release

- **Dev:** `CAP_SERVER_URL=http://<lan-ip>:3000 npm run cap:run:ios` with
  live reload against `next dev`. Cleartext enabled only when URL is http.
- **Preview:** `CAP_SERVER_URL=https://<vercel-preview>` for QA builds.
- **Prod:** default URL. Builds are archived in Xcode → TestFlight, and
  Android Studio → signed AAB → Play internal track, then promoted.
- **Versioning:** `mobile/package.json` version is the single source;
  `scripts/set-version.mjs` writes `MARKETING_VERSION`,
  `CURRENT_PROJECT_VERSION`, `versionName`, `versionCode`. The same version
  appears in the UA suffix.
- **Secrets:** Firebase files, APNs key, Android keystore are outside git.
  Server env adds `FIREBASE_SERVICE_ACCOUNT_JSON`, `MOBILE_MIN_VERSION_IOS`,
  `MOBILE_MIN_VERSION_ANDROID`, `NEXT_PUBLIC_IOS_STORE_URL`,
  `NEXT_PUBLIC_ANDROID_STORE_URL`.
- **CI:** none in v1. Fastlane is a follow-up once releases are routine.

## 12. Testing

### Automated (Vitest, existing mocked-Prisma style)

- `parseNativeUserAgent`: web UA, iOS UA, Android UA, malformed suffix.
- `buildPushPayload`: iOS badge/sound, Android channel, data stringification,
  link default.
- `sendPushToUser`: no devices, `pushEnabled=false`, prunes not-registered
  tokens, swallows SDK errors, missing env → no-op.
- `registerPushDeviceAction` / `unregisterPushDeviceAction`: upsert by token,
  reassigns token between users, requires auth.
- Billing page branch: native renders attention screen, web renders pricing.
- `deleteOwnAccountAction`: removes push devices, calls Clerk delete, blocks
  trainers with active clients, succeeds for trainers with none and for clients.
- Nav items: client and trainer tab sets match the sidebar arrays.

## 13. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Apple rejects as a web wrapper | Native features listed in §10; reviewer notes explain push, deep links, offline |
| Clerk redirect leaves allowed hosts | Enumerate production Clerk domains before first device test; `allowNavigation` wildcard on `*.goinmotus.com` |
| Cold-start push tap event lost | Register listeners synchronously in provider; QA item 4 verifies; fallback deep link via `App.getLaunchUrl()` |
| Store enrollment delays (D-U-N-S, org verification) | Start enrollment in Phase 0, in parallel with code |
| Trainer screens look broken to the reviewer | §5a audit before build; every route is Tier 1, 2, or 3 with no unclassified screens |
| Account deletion cascade complexity | v1 blocks trainers with active clients instead of cascading; client deletion reuses existing deactivation semantics |
| `after()` unavailable in cron/API routes | `sendPushToUser` is awaited directly there with try/catch |
| Remote web view blank on server error | `error.tsx` verified; `errorPath` covers network failure only |

## 14. Phases (for the implementation plan)

0. Accounts & infra in parallel: Apple Developer (org), Google Play (org),
   D-U-N-S, Firebase project, APNs key, Clerk session settings.
1. Web foundation: native detection, provider, legal pages, account deletion,
   nav-items refactor, tab bar, safe areas, native CSS.
1b. Trainer mobile pass: 390 px audit, Tier 1 redesigns, Tier 2 adjustments,
   Tier 3 desktop-only notices (§5a).
2. Native shell: `mobile/` scaffold, config, offline page, icons/splash,
   permissions, version script, dev live-reload workflow.
3. Push: schema, service, actions, provider wiring, pre-prompt, settings
   toggle, triggers, badge.
4. Store rules: billing gate, purchase page, sign-in appearance, downloads
   bridge, external links, version gate, deep links files.
5. QA on devices, listings, TestFlight/internal tracks, submission.
